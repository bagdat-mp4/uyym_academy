# UYYM Academy: схема и границы этапа 1

Этот репозиторий — технический POC до принятия решения о полноценной платформе. Он включает публичный сайт, серверную авторизацию, ручное одобрение браузера, закрытый урок, выдачу небольших частей видео из приватного Google Drive и серверный workflow домашних работ с версиями/оценками. Это не доказательство успешного просмотра реального видео: Supabase, Drive, HTTPS и физические тестовые устройства ещё предстоит подключить владельцу.

Условие перехода к этапу 2: одно реальное приватное видео воспроизводится и перематывается в Chrome/Edge на ноутбуке, Chrome на Android и Safari на iPhone; второй браузер получает отказ; первый ученик не теряет сессию из-за чужого входа; отзыв доступа останавливает выдачу новых фрагментов. Результаты фиксируются в матрице приёмки, а неподдерживаемый браузер получает сообщение без отключения защиты.

## Модель данных

Все времена — `timestamptz`/UTC; отображение учебного расписания — `Asia/Almaty`. Внешний ключ `app_users.id → auth.users.id` закрепляет постоянную идентичность. Номер E.164 может измениться, внутренние связи остаются на `user_id`. Пароли отсутствуют в таблицах приложения, миграциях, журнале и экспортах. Supabase Auth хранит их в собственном защищённом формате.

| Таблицы | Назначение |
|---|---|
| `app_users`, `site_settings` | Роль, активность, обязательная смена пароля, `auth_epoch`, зашифрованный TOTP и хеши recovery codes; публичные настройки без вымышленных данных |
| `courses`, `groups`, `teacher_assignments` | Предмет отдельно от учебного потока; назначения и отдельное разрешение менять доступы своей группы |
| `enrollments`, `payments` | Период и статус доступа отдельно от записей об оплате; уникальность ученик/курс; группа принадлежит тому же курсу |
| `device_bindings`, `login_tickets`, `app_sessions`, `challenges` | Заявка публичного ключа, временный контекст после пароля, настоящая сессия и одноразовые доказательства владения ключом |
| `drive_folders`, `lessons`, `lesson_video_parts`, `playback_grants` | Допустимые приватные папки, серверные Drive ID, короткие fMP4-фрагменты, привязанные разрешения воспроизведения |
| `materials`, `assignments`, `assignment_materials` | Конспекты, архив Quiz/Midterm/Endterm/Final, языки и фильтры, время открытия решений, условия и дедлайны заданий |
| `submissions`, `submission_versions`, `submission_files` | Ответ, история версий, собственная оценка/комментарий; максимум 2 вложения по 5 MiB, уникальные слоты 1 и 2 |

Для материалов и заданий этапа 2 сервер дополнительно проверяет содержимое файлов, MIME и расширение, права пользователя, дедлайн и разрешение на позднее изменение. `.cpp` и `.txt` показываются как текст и никогда не исполняются. Оценка проверяется против максимума задания, а вложенный урок/материал — против курса и группы. Эти проверки нельзя заменить только ограничениями таблиц.

## Проверка доступа к учебному ресурсу

Учебный доступ выдаётся только при выполнении всей цепочки: активный аккаунт → временный пароль изменён → одобренный публичный ключ → актуальная application session → корректный свежий device proof → действующее зачисление нужного курса → активный курс/группа → опубликованный урок/материал → при решении наступившее `solution_opens_at`.

Зачисление действует при `status='active' AND starts_at <= now() AND expires_at > now()`. Результат вычисляется заново при каждом защищённом запросе. Истечение одного курса не закрывает другой действующий курс. `payment_status='paid'` не выдаёт доступ автоматически. Пауза не удаляет историю работ, оценок и просмотра.

Обычный Supabase JWT не является учебным пропуском. Frontend не получает JWT/refresh token Supabase или `service_role`. Сервер использует Auth API только для проверки телефона и пароля и административного создания/сброса аккаунтов. После проверки пароля выдаётся лишь короткоживущий login ticket для смены пароля, подачи заявки и проверки TOTP; учебные таблицы и файлы остаются закрыты.

Все таблицы учебной платформы лежат в `private`, с включённым и принудительным RLS, без политик и без прав `anon`/`authenticated`/`service_role` на схему и таблицы. Используемый сервером `DATABASE_URL` должен быть привилегированным PostgreSQL подключением с BYPASSRLS; его секрет доступен только backend. Это осознанная граница доверия: сервер выполняет все проверки до SQL. Никогда не добавляйте `private` в exposed schemas Supabase Data API и не раздавайте браузеру права на неё. Функции используют INVOKER и закрытый EXECUTE; RPC не обходят backend.

Для runtime предусмотрен отдельный ручной скрипт `supabase/backend-role.sql`: роль `uyym_backend` получает только явно перечисленные права на `private`, без владения таблицами, DDL/TRUNCATE, изменения журнала и членства в `postgres`/`service_role`. Пароль задаётся вне репозитория, через скрытый интерактивный ввод `psql \password`, затем включается LOGIN. Bootstrap создаёт Auth-пользователей через серверный Auth API, поэтому этой роли не требуется SQL-доступ к `auth.users`. Унаследованные всеми ролями права PUBLIC и расширений нужно проверить в конкретном проекте; `search_path` не является границей безопасности. Это следует из [документации Supabase о пользовательских ролях](https://supabase.com/docs/guides/troubleshooting/custom-role-inherits-privileges-that-were-not-explicitly-granted-ddaa1c) и [описания BYPASSRLS](https://supabase.com/docs/guides/database/postgres/row-level-security).

Storage bucket `uyym-private` имеет `public=false` и ограничительные политики запрета для `anon`/`authenticated`. Даже если позднее появится permissive policy, restricted policies сохраняют запрет этому bucket. Backend обращается к Storage с серверными правами после проверки доступа и не выдаёт переносимых signed URLs ученику. Полученный законным способом конспект уже нельзя отозвать.

## Один одобренный браузер

Браузер создаёт ECDSA P-256 ключ через Web Crypto. Приватный CryptoKey создаётся с `extractable=false`, хранится в IndexedDB и не экспортируется. На сервер поступает только публичный JWK. Первое предъявление пароля не одобряет ключ: заявка остаётся `pending` до проверки ученика владельцем.

Сервер создаёт случайный короткоживущий challenge. Подписываемый контекст содержит идентификатор challenge, пользователя, устройство, session или login ticket, `auth_epoch`, назначение, HTTP-метод, точный путь с query string, SHA-256 тела, nonce и время. Метод, путь, тело и контекст сверяются с реальным запросом; сервер проверяет P-256 подпись; одноразовое потребление challenge происходит атомарным UPDATE. Повторное использование или перенос proof на другой endpoint/метод/тело отклоняются. Challenge сам по себе без подписи не выдаёт ресурс.

Случайный opaque session token живёт в `Secure; HttpOnly; SameSite` cookie; база хранит только его хеш. CSRF token дополнительно связан с сессией/тикетом, Origin проверяется сервером. Продление сессии требует нового proof. Перехваченная cookie без приватного ключа не открывает учебный API. IP, User-Agent, локальный device_id и fingerprint не используются как достаточное доказательство. Смена сети разрешена; вкладки одного профиля используют один ключ и одну сессию.

Уникальный индекс допускает один `approved` binding и одну неотозванную application session на пользователя. В POC это более строгое правило применяется также к преподавателю/владельцу. Парольный вход с чужим pending ключом никогда не отзывает законную сессию. Повторная авторизация того же одобренного ключа может заменить только его собственную сессию после успешного proof в транзакции. Выход отзывает сессию, но сохраняет approved binding. Смена/сброс пароля также не освобождают binding. При потере IndexedDB пользователь обращается к владельцу.

Одобрение замены блокирует строку пользователя `FOR UPDATE`, отзывает прежний binding, сессии, login tickets, challenges и playback grants, увеличивает `auth_epoch`, одобряет конкретный новый ключ и пишет журнал в одной транзакции. Уникальные индексы — последняя защита от двух активных записей. Новый браузер повторно входит после одобрения: старый login ticket больше не действителен. Владелец имеет отдельный TOTP/recovery путь; пароль ученика не подменяет этот путь.

Сообщение чужому браузеру: **«Бұл аккаунт басқа құрылғыға тіркелген. Құрылғыны ауыстыру үшін әкімшіге хабарласыңыз»**.

Сайт связывает браузерный профиль с криптографическим ключом. Он не читает MAC, IMEI или серийный номер и не определяет физический компьютер с абсолютной точностью. Это снижает обычную передачу телефона/пароля другу; не предотвращает запись экрана, отправку скачанного материала, удалённое управление одобренным устройством и специально модифицированный клиент. Синхронизируемый passkey не используется как доказательство одного физического устройства.

## Видео: приватный Drive → backend → плеер

Папки Drive имеют Restricted доступ: владелец, серверная identity и необходимые доверенные преподаватели. Учеников не добавляют в Drive permissions. Google file ID, исходные URL, access/refresh tokens и credentials не выходят в браузер. Backend проверяет принадлежность выделенной папке, MIME, размер и permissions перед публикацией; любая публичная или неподходящая permission блокирует публикацию. Ошибка API закрывает доступ.

Исходный MP4 необходимо проверить/перекодировать в H.264 + AAC, затем локально подготовить fMP4 init segment и короткие медиафрагменты. Они сохраняются в той же приватной области Drive; оригинал остаётся исходником. `lesson_video_parts` хранит Drive ID только на сервере, порядок, время и размер. В POC один фрагмент ограничен 1 MiB; это верхний предел буфера и длительности отдельной сетевой выдачи, а не лимит всего урока.

Плеер использует JavaScript fetch и MediaSource. Fetch может отправить proof; обычный `<video src>` не может добавить произвольную подпись к каждому запросу. Перед началом запрашивается привязанный grant, затем для init/каждого нового фрагмента создаётся и подписывается свой challenge. Backend проверяет пользователя, ключ, сессию, epoch, grant, курс, срок, публикацию и heartbeat, получает разрешённую часть через Drive `files.get?alt=media` с ограниченным Range и передаёт поток без чтения многочасового файла в память. Grant не является самостоятельным пропуском. Ответы защищённых endpoint получают `Cache-Control: no-store`.

Перемотка выбирает фрагменты по временной шкале; новые порции буферизуются в ограниченном окне. У плеера есть управление скоростью, звуком и полноэкранным режимом; кнопка скачивания скрыта. Метка содержит имя и маскированный телефон. После отзыва аккаунта/курса/устройства следующие части запрещены. Уже полученные байты невозможно отозвать, поэтому абсолютное мгновенное выключение изображения не обещается. Это не DRM.

Safari должен поддерживать используемый MediaSource/ManagedMediaSource и кодек; при отсутствии поддержки показывается объяснение. Проверка совместимости проводится на реальном iPhone, не заменяется user-agent spoofing или эмуляцией desktop браузера.

## Обязательная проверка и предел доказательств

Автоматические проверки отдельно подтверждают SQL-ограничения, транзакции, однократность challenge, проверку proof и границы привилегий. Embedded PostgreSQL проверяет миграции на реальном движке, но не заменяет живой Supabase Auth, его настройки регистрации и grants, Google Drive permissions/quotas или проверку двух физических устройств.

`tests/api.test.ts` также вызывает настоящие маршруты Fastify через `app.inject`, выполняет SQL на embedded PostgreSQL и подписывает реальные challenges через Web Crypto с неэкспортируемым приватным P-256 ключом. Внешние ответы Supabase Auth для телефона/пароля и смены пароля явно симулируются; Drive не симулируется и успешное получение бинарного видео в этих тестах не заявляется. Проверяются TOTP владельца и отказ повторного кода, ручное одобрение/замена через ADMIN endpoint, невозможность использовать чужую cookie с другим ключом, отсутствие вытеснения, CSRF, replay, границы курса/группы преподавателя, скрытие Drive ID в playback manifest, непереносимость grant и отказ выдачи после паузы/отзыва. PGlite использует последовательный SQL transport; реальные гонки нескольких PostgreSQL connections остаются в живой приёмке.

Перед выпуском необходимо проверить: чужой парольный вход не вытесняет ученика; logout/смена пароля/очистка браузера не освобождают binding; одобрение замены отзывает прежний ключ; cookie без proof не открывает данные; replay и параллельное одобрение не дают двойной доступ; прямой Supabase JWT/Storage/RPC не открывает private данные; чужой lesson/file не открывает другой курс; блокировка прекращает новые фрагменты; секреты отсутствуют в frontend/Git. На этапе 2 добавлены проверки панели управления и чужих групп преподавателя. Сохранение работ/оценок относится к будущему учебному этапу; восстановление backup проверяется отдельно.

До подключения внешних систем результаты живого POC должны оставаться «не выполнено». Платные ресурсы и тарифы нельзя подключать автоматически. 400 GB Drive — ёмкость хранения, а не обещание бесплатного видеотрафика; стоимость media backend и действующие условия сервисов оцениваются отдельно в инструкции владельца.

## Этап 2: управление и согласование операций

ADMIN управляет пользователями, курсами, группами, назначениями, зачислениями, ручными оплатами, браузерами, настройками и журналом через подписанные BFF API. TEACHER получает только свои назначения и roster конкретной назначенной группы. Изменение существующего зачисления требует отдельного действующего `can_manage_access`; создание пользователей, перенос между группами, роли, оплаты, настройки и браузеры ему недоступны. Снятие назначения проверяется при следующем запросе, включая повтор ранее выполненной операции.

Управляющая транзакция сначала получает общий advisory lock, затем заново проверяет application session, активность пользователя, epoch, approved key и роль; объектный scope проверяется внутри той же транзакции. Триггеры групп/зачислений получают этот lock до блокировок строк. Вместимость учитывает будущие и приостановленные ещё не истёкшие записи; перенос и изменение вместимости используют тот же порядок. `revision` предотвращает потерю параллельных изменений, `mutation_receipts` сохраняет только минимальное безопасное подтверждение повтора. Детали и предел доказательства конкурентности — в `management-guide.md`.

Удалённый Supabase Auth нельзя включить в локальную SQL-транзакцию. `auth_operations` хранит безопасное намерение со стабильным UUID, lease и состоянием, без пароля/токена. Сброс сначала блокирует учебный доступ, отзывает старые сессии и сохраняет ключ; затем меняет Auth и завершает локальное состояние. Неоднозначный результат остаётся закрытым до согласования. Предвыделенный Auth ID и административный marker позволяют завершить потерянный ответ без дубликата; исходный пароль не восстанавливается. Явный повтор не отменяет потенциально поздний commit внешнего сервиса, что отражено в инструкции.

Оплаты и доступ независимы. Исходная оплата и корректировки неизменяемы; ошибка исправляется новой версией с причиной. Очистка обслуживает только устаревшие временные security-строки ограниченными пачками; зачисления, approved keys, журнал, квитанции и Auth-операции сохраняются.
