# Isolated teacher MP4 upload staging

This procedure runs the PR #12 code locally with a fresh in-memory PGlite database, synthetic ADMIN/TEACHER/STUDENT accounts, and a separate Google Cloud OAuth client. It does not connect to production Supabase, Render, or `uyym.app`. Migration 009 is applied only to the disposable local database. The fixture permits only Google Drive API/upload/download URLs plus the exact OAuth token and signing-certificate endpoints needed for login; token exchange rejects redirects, and Drive download redirects are validated and stripped of Authorization when crossing origins.

## One-time Google setup

1. Reuse the existing `uyym-academy-drive` project and the already-created `UYYM Staging Local` Web OAuth client. Do not edit the production `UYYM Academy Drive` client or create another project. Add this exact Authorized redirect URI to the staging client only:

   `http://localhost:5174/api/drive/oauth/callback`

   Keep the consent screen in Testing and add only the Drive owner account as a test user if it is not already listed. Use the staging client ID and secret only for this local harness. The app requests `openid`, `email`, and `drive.file`.
2. Reuse the already-created `uyym-staging-reader` service account; do not edit or reuse production `uyym-drive-reader`. In the Cloud Console, open `uyym-staging-reader` → **Keys** → **Add key** → **Create new key** → **JSON**. Save the downloaded key directly at:

   `%LOCALAPPDATA%\UYYM\DriveStaging\service-account.json`

   First run the local launcher in key-only mode; it creates both `%LOCALAPPDATA%\UYYM` and this directory with protected NTFS ACLs granting Full Control only to your current Windows account and `SYSTEM`, then stops with `STAGING_SERVICE_ACCOUNT_KEY_REQUIRED` without asking for OAuth details or starting a server:

   `& .\scripts\Start-DriveStaging.ps1 -ImportKeyOnly`

   Create the key and save it directly in that directory so the JSON inherits this ACL. If it is already in Downloads, copy it (do not move it) into the protected directory; the launcher checks the destination file owner, ACL, and reparse-point status. Before encrypting, it verifies `type`, token endpoint, private-key shape, and the exact identity `uyym-staging-reader@uyym-academy-drive.iam.gserviceaccount.com`; it repeats the identity check after DPAPI decryption. It rejects the production account and keys from any other project. It imports the key into `service-account.dpapi` using Windows DPAPI CurrentUser and an atomic create-new write, without overwriting an existing file. It then asks whether to delete the plaintext JSON; answer `YES` to continue. If you decline, it removes the newly created encrypted copy and stops. File deletion is best effort and does not guarantee secure physical erasure. Never copy a production service-account key into this directory.
3. Only when ready to start the local staging app, and without yet uploading, run from a local PowerShell window in this PR #12 checkout:

   `& .\scripts\Start-DriveStaging.ps1`

   Enter the Google owner email, staging OAuth client ID, and OAuth client secret in its local prompts. The client secret is hidden and is passed only in the staging server process environment; it is not placed in command arguments, output, Git, or a project `.env`. The launcher DPAPI-decrypts the service-account key into memory for the server process and starts Vite with a separate environment containing only `NODE_ENV`. The staging Vite config disables `.env` loading (`envDir: false`) and custom environment exposure (`envPrefix: []`), and binds only to `127.0.0.1:5174`; its `/api` proxy targets the fixture backend at `127.0.0.1:18878`. The fixture backend uses in-memory PGlite and simulated Auth, never production Supabase. It clears byte buffers and its child-environment collection best-effort; .NET strings and child-process environment values cannot be guaranteed erased from memory. The staging server enforces a two-hour lifetime; closing the PowerShell window or pressing Ctrl+C stops its child processes through cleanup.

## Real acceptance

1. Open `http://localhost:5174`. The local-only endpoint `http://localhost:18878/__ui/staging-login` returns synthetic login values and a current synthetic ADMIN TOTP; it contains no real accounts. Use those values locally; production account credentials are not valid in the simulated staging Auth. Sign in as the local ADMIN and complete the existing TOTP browser approval. Connect the staging Google owner account and approve the Google consent screen. The app verifies and reuses the immutable staging root ID saved by the launcher; it never chooses among same-named folders or creates another root.
2. In ADMIN, enable uploads for the synthetic teacher. Sign in as the synthetic teacher to create a pending browser request, then use ADMIN → browser requests to approve that exact request through the normal authenticated management route. Re-enter the same synthetic credentials in the same browser profile. Choose the seeded Calculus I / CALC A assignment and a newly named, small synthetic MP4 distinct from previous uploads. Enter a distinctive lesson title, then click Upload and Publish. Confirm the Preparing, Uploading, Verifying, Publishing and Published states. Publication is automatic only after the existing server verifies the completed file. Do not select or adopt the previous `staging-test.mp4` orphan.
3. In the owner's Drive, verify the staging folder/course/week path, MP4 owner, and restricted permissions: the owner is `owner`, the staging service account is `reader`, and no public or extra users are present. The teacher must not have direct Drive access.
4. After the teacher screen confirms Published, sign in as the synthetic student to create a pending browser request, approve that exact request from the synthetic ADMIN account through the normal browser-request flow, then re-enter the student credentials in the same browser profile. Refresh My Courses → Calculus I. Open the distinctly titled new lesson and verify the first frame, advancing playback, and a seek from about 2 seconds to 8 seconds. Check that the playhead advances after the seek. Do not treat a visible Play button as successful playback. Confirm the browser receives media through the UYYM local BFF and never receives a Drive file ID, OAuth token, or resumable session URI.

This real Google run is still a local app test: Supabase Auth is replaced by the synthetic fixture and the database is PGlite in memory. It does not establish production Supabase, Render, or cross-device acceptance. The encrypted OAuth refresh token exists only in the ephemeral local DB and disappears when the local server stops. After the test, stop the launcher, revoke/delete only the `uyym-staging-reader` key in Cloud Console, and delete `%LOCALAPPDATA%\UYYM\DriveStaging\service-account.dpapi`; deletion does not guarantee physical erasure. Also remove the staging Drive root and uploaded MP4 if you no longer need them. Do not revoke or delete the production OAuth client or `uyym-drive-reader` key.

On 2026-11-03 the owner reported a completed real staging upload, automatic publication, student visibility in Calculus I, and active MP4 playback. The sanitized upload log recorded a final Google HTTP 200 and no reader-verification HTTP 503. The browser remained user-operated because Browser Use denied localhost access. A seek after playback and a real unauthorized-student denial were not confirmed; keep those checks open. Preserve the working staging session and existing Drive files until the owner separately approves cleanup.

## Fresh-session acceptance gate

The reviewed launcher requires interactive entry of the existing staging OAuth client credentials. Never enter them in chat. A successful PowerShell process launch alone does not establish that the backend is ready. Confirm the launcher ready message and both loopback listeners. Browser Use denial still requires the normal user-operated UI; do not use direct HTTP or another automation surface to bypass it. Synthetic tests are not evidence of real Drive upload or browser playback. No cleanup of the earlier Drive MP4 is authorized by starting a fresh session.

## Persistent staging root identity

A fresh local PGlite database forgets its Drive root. Earlier launches created several folders with the same staging name. The updated launcher now asks once for the exact ID of an **existing** staging root and saves it in the private `%LOCALAPPDATA%\UYYM\DriveStaging\root-folder-id.txt` file. It refuses to overwrite that file. On subsequent starts it reuses the saved ID. The OAuth connection verifies that the ID is an owner-owned, untrashed folder with the expected name and exactly the owner and `uyym-staging-reader` Reader permissions; it does not pick a folder by name or grant missing permissions to a chosen existing folder. No new staging root is created.

Before entering an ID, use the owner's Drive UI to identify the folder containing the intended existing upload and check its sharing. If several same-named folders remain and none can be verified, do not choose one arbitrarily. Existing folders/files are preserved. The currently running local server keeps its in-memory IDs until it stops; this change takes effect only after an approved restart.

The staging folder hierarchy is keyed by the verified root ID and private Drive `appProperties` markers: `course:calculus-i` and `week:calculus-i:1`. The visible child names are `Calculus I` and `Week 01`. A fresh fixture rediscovers a single exact marked child under its verified parent; missing markers create a new child, and duplicate matches fail closed. Existing unmarked children are preserved.
