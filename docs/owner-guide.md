# Инструкция владельцу: подключение и POC

Начните с одного своего приватного видео и отдельного тестового ученика. Выполните приёмку `poc-acceptance.md`, прежде чем загружать все записи и начинать учебную эксплуатацию. Настройка ниже не покупает услуги и не подтверждает работоспособность внешних сервисов автоматически.

## 1. Локальная среда и Supabase

1. Установите Node.js 22+ и Git. В корне проекта выполните `npm ci`, `npm test`, `npm run build`.
2. Создайте бесплатный Supabase проект. В Auth включите phone provider, отключите **Allow new users to sign up**. OTP/SMS endpoints не используются; платный SMS провайдер не нужен этому административному процессу.
3. Примените в SQL Editor по порядку файлы `supabase/migrations/202610100001_private_platform.sql`, `202610100002_atomic_security.sql`, `202610100003_private_storage.sql`. Только для нового проекта: миграции не предназначены для перезаписи существующих данных.
4. Не добавляйте `private` в exposed schemas Data API. У `anon`/`authenticated`/`service_role` нет SQL-доступа к этой схеме. Storage bucket `uyym-private` закрыт для browser JWT; будущий backend Storage доступ будет отдельно проверять права.
5. Примените `supabase/backend-role.sql` как оператор БД. Роль создаётся NOLOGIN; в интерактивном `psql` выполните `\password uyym_backend`, затем `ALTER ROLE uyym_backend LOGIN;`. Пароль не записывайте в SQL/историю shell. BYPASSRLS нужен только доверенному BFF, который проверяет пользователя и scope. Роль не получает DDL/auth.users или права изменения журнала. Проверьте её фактические права в своём Supabase, включая публичные права расширений.
6. В игнорируемый `.env` поместите `DATABASE_URL` из direct/session pooler с этой ролью, SSL и проверкой сертификата (не используйте `rejectUnauthorized:false`), `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`. Service key нужен только серверному Auth Admin API; в frontend нет Supabase клиента.
7. Сгенерируйте `ADMIN_ENCRYPTION_KEY`: `node -e "process.stdout.write(require('crypto').randomBytes(32).toString('hex'))"`. Сохраните 64 hex символа в серверном secret store. Это ключ AES-GCM для TOTP, отдельно от резервной копии БД.
8. Для dev: `APP_ORIGIN=http://localhost:5173`, `COOKIE_SECURE=false`. Откройте именно `localhost`; `127.0.0.1` — другая Origin.

Все Supabase токены остаются внутри BFF; приложение использует свой случайный session cookie, а в БД — его SHA-256. Прямой успешный Auth login с другим браузером обязан по-прежнему получать отказ к учебным таблицам и файлам.

## 2. Защищённое создание первого администратора

В локальном интерактивном терминале выполните `npm run bootstrap`. HTTP bootstrap endpoint отсутствует. Скрипт под блокировкой проверит, что ADMIN ещё нет, запросит проверенный телефон и имя, создаст случайный пароль и TOTP secret. Добавьте secret в authenticator и введите проверочный код: ввод скрыт.

После подтверждения скрипт один раз покажет временный пароль и десять recovery codes. Передайте/сохраните их офлайн; не публикуйте терминал и скриншоты. В таблицах приложения нет пароля, recovery codes хранятся как хеши, TOTP secret шифруется. Первый вход требует сменить временный пароль и ввести TOTP. Только TOTP владельца разрешает регистрацию его собственного браузера; учащиеся всегда ждут ручного решения.

Повторный bootstrap при существующем ADMIN отклоняется. Скрипт не создаёт дополнительные роли ADMIN и не может незаметно заменить владельца.

## 3. Подключение приватного Drive

Создайте Google Cloud проект, включите Drive API. Создайте service account без domain-wide delegation и без доступа ко всему диску. Дайте его email Viewer только отдельной папке курса, если ваш аккаунт/организация допускает такое sharing. Исходное видео, init и сегменты должны находиться непосредственно в этой разрешённой папке. General access — **Restricted**.

Доступ разрешён только владельцу, backend identity и перечисленным доверенным преподавателям. Студенты Drive permissions не получают. Код намеренно отклоняет domain/group/anyone, неразрешённые email и неизвестный ACL. Для иных организационных схем нужен отдельный адаптер и тест; публичная ссылка не является обходным решением.

JSON service account храните **вне checkout**, с правами чтения только процесса BFF. В `.env` задайте абсолютный `GOOGLE_APPLICATION_CREDENTIALS`, список `DRIVE_ALLOWED_FOLDER_IDS` и `DRIVE_ALLOWED_PERMISSION_EMAILS` (email владельца, backend, реальных доверенных преподавателей). Укажите каждого фактического principal ACL. API scope — `drive.readonly`; папки проверяются и при публикации, и перед новой частью видео. У backend нет функции открыть публичный доступ при ошибке.

## 4. Пользователи, группа и доступ

После личной проверки телефона владельцем:

```powershell
npm run owner -- create-user
npm run owner -- create-group
npm run owner -- assign-teacher
npm run owner -- enroll
```

Каждая команда проверяет TOTP владельца и запрашивает поля интерактивно. `create-user` создаёт STUDENT или TEACHER с индивидуальным случайным временным паролем; существующие пароли недоступны. Передайте его только проверенному человеку. Не экспортируйте его в CSV или журнал.

Для `course_id` посмотрите `private.courses` в операторском SQL Editor: три начальных курса уже добавлены. `create-group` возвращает `group_id`, `create-user` — постоянный `user_id`. Назначение преподавателя содержит отдельное `can_manage_access`; UI изменения доступа преподавателем будет реализован на следующем этапе.

`enroll` устанавливает active и UTC интервал, отдельно от payment_status. Оно не отмечает оплату автоматически. Пример времени: `2026-10-12T00:00:00Z`; UI отображает Asia/Almaty. Сейчас зачисление/продление выполняется CLI владельца; полноценная админка оплат и пользователей — следующий этап.

`npm run owner -- pause` сохраняет историю и приостанавливает выбранное зачисление. Другой активный курс ученика остаётся доступен. `npm run owner -- settings` добавляет только реальные WhatsApp/email; пустые значения оставляют контактные кнопки недоступными.

## 5. Одобрение конкретного браузера

Ученик входит с выданным телефоном/паролем, меняет временный пароль. Браузер создаёт локальный неэкспортируемый P-256 CryptoKey; сервер получает только public JWK и заявку. До решения доступны настройка аккаунта и статус — учебные файлы закрыты.

Владелец входит с TOTP, открывает список браузеров. Сверьте ученика по существующему личному контакту и конкретную заявку/отпечаток ключа. Название `Chrome · Windows` предоставлено клиентом и само по себе ничего не доказывает. Нажмите одобрение только после проверки человека. После решения ученик **входит заново в том же браузере**: старый pre-auth ticket отозван.

Правильный пароль второго браузера создаёт заявку и показывает отказ, но не закрывает сессию первого. На одобренном браузере несколько вкладок используют общий ключ и cookie. Logout, истечение сессии, смена IP и сброс пароля не снимают привязку. Потеря IndexedDB/очистка данных требует решения владельца.

## 6. Реальное видео, перемотка и отзыв

Установите FFmpeg из официального источника; скрипт требует `ffmpeg` в PATH. Используйте реальный локальный MP4 с видео и аудио. Подготовка не скачивает Drive-запись автоматически:

```powershell
npm run prepare-video -- "D:\Records\lesson.mp4" "work\prepared-video"
```

Скрипт создаёт H.264 baseline/AAC 720p, init.mp4 и примерно четырёхсекундные fMP4 `.m4s`, проверяет размер каждой части до 1 MiB, сохраняет codec и timeline в manifest.json. Используйте пустую выходную папку: перезапись файлов отключена. Исходники обычного MP4 можно сохранять fast-start для архивной совместимости, но подписанный MSE поток использует подготовленные фрагменты — одного fast-start недостаточно.

Загрузите init + все m4s в тот же Restricted Drive folder, что и исходный MP4. Не давайте ученикам permission или manifest. В локальном `manifest.json` добавьте каждому part поле `drive_file_id` с фактическим ID загруженного файла. Затем:

```powershell
npm run register-video -- "work\prepared-video\manifest.json"
```

CLI проверяет TOTP, timeline, исходный MP4, реальный размер/MIME/ACL каждой части, курс/группу, атомарно создаёт урок. Неправильные permissions или API ошибка прекращают публикацию. Клиент получает только lesson_id, разрешение платформы и временной индекс без Drive IDs.

Плеер получает каждый ограниченный Drive Range через BFF с новым proof. Grant связан с user/session/device/epoch; одной скопированной ссылки недостаточно. Сервер перепроверяет права после получения Drive response headers перед выдачей части. После паузы/отзыва новые части не выдаются; текущие до 1 MiB и уже полученный буфер нельзя вернуть. Скорость, звук, перемотку, fullscreen и Safari нужно проверить на реальной записи.

## 7. Замена и восстановление

Для замены ученик входит в новом браузере и связывается с владельцем. Новая заявка не открывает уроки. Одобрение атомарно отзывает старый ключ, application sessions, tickets и playback grants, увеличивает auth_epoch. Новый браузер входит заново. Все изменения записаны в журнал.

`npm run owner -- revoke-device` отзывает текущую привязку без одобрения новой. `npm run owner -- reset-password` после личной проверки личности выдаёт новый временный пароль и закрывает sessions/grants, сохраняя одобренный public key. Это не способ пересесть на другой браузер.

Если владелец потерял authenticator/браузер, на доверенном сервере с доступом к конфигурации выполните `npm run owner -- recover-admin`. Нужен офлайн одноразовый recovery code. Скрипт проверяет новый TOTP, отзывает старые ключи/сессии, создаёт новый временный пароль и новый набор recovery codes. Старые коды отзываются. Recovery HTTP endpoint отсутствует. При утрате и recovery codes, и безопасного серверного доступа нельзя автоматически ослаблять защиту; используйте проверенное операторское восстановление из backup.

Supabase Auth и PostgreSQL — два отдельных сервиса: их изменение не является распределённой транзакцией. При ошибке CLI/сети после смены Auth пароля остановите запуск, проверьте профиль/сессии и повторите административный reset. Не считать такую ошибку успешным восстановлением; проверка отказов входит в приёмку.

## 8. HTTPS и домен

`npm run build`, затем `npm start` за HTTPS reverse proxy одной Origin. Production `.env`: `NODE_ENV=production`, `COOKIE_SECURE=true`, `APP_ORIGIN=https://ваш-домен`. Backend слушает только loopback. Прокси обязан перезаписывать X-Forwarded-For; включите `TRUST_LOCAL_PROXY=true` только для своего локального прокси. Это позволяет rate limiter видеть реальные IP и не доверять произвольным forwarded headers.

Прокси не кеширует `/api/*`, не хранит многомегабайтные ответы целиком, передаёт поток и имеет ограниченные таймауты. Не размещайте приватное видео через бесплатный CDN/Tunnel вопреки условиям. Выбор тарифа, домена и продление описаны в `costs-and-hosting.md`; платный ресурс не активируется кодом.

## 9. Backup и проверка восстановления

- Регулярно делайте шифрованный backup всей Supabase БД, включая private schema и поддерживаемый экспорт Auth. Обычная копия только public schema теряет учебные данные и FK user IDs. Согласуйте поддерживаемый метод Auth restore с актуальной документацией Supabase.
- Храните отдельную зашифрованную копию конфигурации/ADMIN_ENCRYPTION_KEY и офлайн recovery codes. Не складывайте ключ шифрования рядом с незашифрованным dump. Drive исходники/части и будущий Storage bucket требуют отдельной копии.
- Не копируйте production пользователей в общедоступный тестовый проект. В изолированном восстановлении выключите уведомления/внешнюю публикацию, восстановите миграции/таблицы/identity IDs и grant права BFF.
- После восстановления отзовите все app_sessions/login_tickets/playback_grants и увеличьте auth_epoch; опубликованные ранее cookies должны перестать работать. Сохраните approved ключи только если политика восстановления этого требует, но повторно проверьте владельца.
- Подтвердите FK, закрытые grants/RLS, TOTP/recovery, отсутствие публичного Drive, одно тестовое зачисление и реальное воспроизведение с отказом второго браузера. Запишите время, дату и результат пробного restore. Пока restore не был выполнен, резервное восстановление считается **непроверенным**.
