# Teacher video uploads to the owner's Drive

Status: local implementation only. Migration `202610310009_owner_drive_upload.sql` has **not** been applied to the live database by this work, and no Google OAuth account has been connected or live file uploaded. Do not enable the teacher permission until the real acceptance checks below pass.

## How it works

- ADMIN connects the **configured owner's** Google account once in UYYM. Google OAuth uses `openid`, `email`, and `drive.file`. The backend verifies the Google account email against `DRIVE_OWNER_EMAIL`, then creates a private `UYYM Academy private lessons` folder in that owner's My Drive and grants the existing backend service account **reader** access. Files created with the owner's OAuth token belong to the owner and use the owner's quota.
- ADMIN enables video upload for individual TEACHER accounts. A teacher needs only a UYYM account and a current course/group assignment. They do not sign in to Google, and browser responses never include the owner's OAuth tokens, the Drive file ID or the Google resumable session URI.
- A teacher chooses an assigned course/group, week, title and MP4. UYYM creates a **draft** lesson. The browser sends 1 MiB pieces to the UYYM backend. Each request has a fresh approved-browser proof, CSRF/session check and teacher assignment/permission check. The backend relays that bounded piece to Google's resumable upload session. The session URI and owner's refresh token are encrypted at rest in private tables.
- The backend checks the completed file's owner, parent, MIME, size, permissions and service-account readability before attaching it to the draft lesson. The teacher publishes the lesson separately. Students receive native MP4 ranges through the existing BFF, session-bound playback grant, signed browser proof, enrollment check and per-range Drive validation. Existing fragmented videos retain their current player path.
- Revoking a teacher's upload permission prevents their subsequent chunks and starts. It does not change the upload permissions of other teachers or revoke a student's already published lesson. An in-flight chunk may complete before the revocation transaction returns.

## Owner setup before enabling

1. Create a Google Cloud OAuth **Web application** client in an account controlled by the owner, enable the Drive API, and configure the consent screen. Use the exact production redirect URI `https://uyym.app/api/drive/oauth/callback`. If using a temporary staging origin, register its callback URI separately. The owner must be an authorized test user while the Google consent screen is in Testing mode. Google's current Testing mode may make offline refresh tokens expire after seven days; verify the chosen consent-screen state before relying on unattended uploads.
2. Keep the existing Drive **read-only** service-account credentials server-side. Confirm that the owner's personal Drive can grant that service account reader access to the private UYYM folder. The service account must never own uploaded files. If sharing is unavailable, this implementation must be adapted and retested before enabling uploads.
3. In the hosting provider's protected environment settings, supply `DRIVE_OWNER_USER_ID` (permanent UYYM user UUID for the owner), `DRIVE_OWNER_EMAIL`, `DRIVE_OAUTH_CLIENT_ID`, `DRIVE_OAUTH_CLIENT_SECRET`, and a separate random 32-byte hex `DRIVE_OAUTH_ENCRYPTION_KEY`. Keep existing `APP_ORIGIN`, `GOOGLE_APPLICATION_CREDENTIALS` (or `GOOGLE_APPLICATION_CREDENTIALS_BASE64`) and Drive credentials. `DRIVE_ALLOWED_PERMISSION_EMAILS` must include the owner email and the backend service-account email. No value belongs in Git, public JavaScript or a ticket. Changing the OAuth encryption key without re-encrypting stored values breaks the connection and resumable sessions.
4. Apply `supabase/migrations/202610310009_owner_drive_upload.sql` through the owner's approved database migration procedure. It adds private tables with forced RLS; the public Supabase roles have no access. Verify that the actual `DATABASE_URL` role has backend grants and RLS bypass as in earlier migrations. This step is a **production data/schema change** and was not performed here.
5. Deploy only after separate release approval. In the ADMIN UYYM panel open **Teacher video uploads**, connect the owner Drive from the approved owner browser, and confirm that the connection succeeds. Other ADMIN users can view status, but cannot initiate or finish the owner's OAuth connection.

## Real acceptance before use

Use one small, private Teams recording, preferably MP4 with H.264 video, AAC audio and fast-start metadata. Check actual codecs; an `.mp4` extension or `ftyp` header alone does not guarantee playback on all supported devices.

1. Assign a teacher to only the intended course/group, then enable that teacher's video-upload permission. The teacher uploads one MP4, interrupts and resumes once, and sees progress. Test both a normal-sized file and a long file; Render Free bandwidth, request limits and Google quotas have **not** been measured here. No whole-video file should appear on Render disk.
2. In the owner's **personal** Drive, confirm `UYYM Academy private lessons / <course> / Week NN / <file>` and that the owner is the file owner. Confirm that quota usage increases in the owner's account. Check that folder/file permissions remain restricted to the owner and intended backend reader; a teacher must have no direct Google access. Do not publish if these checks fail.
3. Confirm the draft is invisible to a STUDENT. Publish it. In a **real approved STUDENT browser** with an active enrollment, test first frame, seek, heartbeat and playback after page refresh. Test Chrome/Edge desktop, Android and Safari iPhone. Verify a different browser, copied cookie and expired/paused enrollment cannot receive a new range. After access revocation, new parts must fail; already buffered bytes cannot be recalled. Confirm legacy videos still play.
4. Revoke upload permission for one teacher and verify that their next chunk/start fails while a different enabled teacher can still upload. Check the ADMIN activity log without exposing tokens or Drive IDs.
5. Review operational cost and limits before any wider rollout. Drive storage capacity does not provide unlimited video delivery or guarantee that Render Free is suitable for large uploads. Monitor service bandwidth and Google API quota. Do not enable a paid service without the owner's choice.

## Recovery

- A failed network transfer can be resumed while the same Google upload session remains valid: the teacher selects the same local file and the backend queries Google's current offset. If the Google session expires, start a new upload; the previous draft can be left unpublished for admin cleanup.
- Keep the OAuth encryption key in protected backup alongside the encrypted database backup. Back up and test restoration of the private tables before rotating the key. The Google owner can revoke OAuth access in their Google account; this stops new uploads until the owner reconnects.
- Do not store a Google access token, refresh token, resumable URI, source URL or backend service-account JSON in a client log, browser storage, public error or repository.
